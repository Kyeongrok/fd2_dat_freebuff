# ANI.DAT 포맷 분석 (수정판)

## 파일 구조

```
오프셋 0x00-0x05: 매직 "LLLLLL"
오프셋 0x06-0x07: 인덱스 수 (WORD) = 46 (유효한 것은 9개)
오프셋 0x08-0x09: 예약
오프셋 0x0A+:     인덱스 테이블 (4바이트 항목)
```

## 인덱스 테이블

**포맷**: 각 4바이트 항목은 AFM 데이터의 오프셋 값

**공식**: `offset = 4 * index + 6`

**유효 인덱스**:

| 인덱스 | 오프셋 주소 | 프레임 수 | 설명 |
|--------|------------|----------|------|
| 0 | 0x0000002E | 96 | 첫 번째 AFM (시작 애니메이션?) |
| 1 | 0x000F4D5E | 51 | 인덱싱됨 |
| 2 | 0x0019018E | 26 | 기존 분석에서 발견되지 않음 |
| 3 | 0x001A7F4C | 28 | 인덱싱됨 |
| 4 | 0x001B0A3A | 12 | 기존 분석에서 발견되지 않음 |
| 5 | 0x001B974B | 35 | 인덱싱됨 |
| 6 | 0x0021DCEA | 12 | 기존 분석에서 발견되지 않음 |
| 7 | 0x0022870B | 17 | 인덱싱됨 |
| 8 | 0x0024A18E | 12 | 기존 분석에서 발견되지 않음 |

## 로딩 함수 분석 (sub_20421)

```c
// 1. 파일 열기
_rb_ = fopen("ANI.DAT", "rb");

// 2. 인덱스 읽기
fseek(_rb_, 4 * a5 + 6, 0);  // a5 = 인덱스 번호
fread(v8, 1, 8, _rb_);       // 8바이트 읽기

// 3. AFM 데이터로 이동
fseek(_rb_, *(DWORD*)v8, 0); // 앞 4바이트를 오프셋으로 사용

// 4. AFM 헤더 읽기
fread(v8, 1, 173, _rb_);     // 173바이트 헤더 읽기
frame_count = *(WORD*)(v8 + 165);  // 프레임 수는 오프셋 0xA5

// 5. 프레임 반복 읽기
for (i = 0; i < frame_count; i++) {
    fread(frame_header, 1, 8, _rb_);  // 프레임 헤더
    fread(frame_data, 1, size, _rb_); // 프레임 데이터
    sub_36FF4(param, frame_data);     // 프레임 디코딩
}
```

## 기존 분석의 오류

기존에는 인덱스 테이블이 8바이트 항목 (start, end) 형식이라고 판단했습니다. 이는 다음 이유 때문입니다:
- 연속된 두 개의 4바이트 항목을 읽으면 인접한 두 AFM의 오프셋이 됨
- 예: index=0 시 8바이트 읽으면 [0x2E, 0xF4D5E] — [start, end] 처럼 보임
- 실제로는 독립적인 두 인덱스 항목

## 결론

9개의 AFM 리소스 모두 인덱스 테이블에 포함되어 있으며, 인덱스 테이블은 4바이트 항목 형식을 사용합니다.
